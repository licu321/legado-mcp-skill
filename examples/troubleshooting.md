# 示例：常见错误排查（troubleshooting）

> 问答式示例。每个示例遵循统一流程：**分类 → 最小必要工具 → 多轮排查 → 输出结论**。
> 覆盖 Skill 要求的所有错误类别：401、连接失败、超时、未找到、调试通道占用、JS 错误、Cookie 异常、批量校验未完成。

---

## 示例 1：401 认证失败

**用户**：*“连接报 401 Unauthorized，说令牌不对。”*

1. 分类 → **E1 认证失败**。
2. 最小工具：核对令牌后重试 `list_sources`。
3. 排查：确认 `X-Legado-Token` 与 App“Web 与 MCP 访问令牌”完全一致（含大小写）；确认令牌保护开启且未省略请求头。
4. 结论：
   ```
   - 根因：请求头中的令牌与 App 配置不一致（多了一个尾随空格）。
   - 证据：401 + “MCP 访问令牌未配置或不正确”。
   - 修复建议：去掉尾随空格，重发 X-Legado-Token。
   - 验证方式：重试 list_sources，应返回书源数量。
   ```

## 示例 2：连接失败

**用户**：*“连不上 http://192.168.1.100:1236/mcp，提示 Connection refused。”*

1. 分类 → **E2 连接失败**。
2. 最小动作：检查服务状态与网络，重试连接。
3. 排查（一次一项）：
   - MCP 服务开关是否打开？（App 通知栏可见服务地址）
   - 设备 IP 是否变化？（切 WiFi 后 IP 变）
   - 端口是否被改？（默认 1236）
   - 是否同一局域网、防火墙是否放行。
4. 结论：
   ```
   - 根因：手机切换 WiFi，IP 由 192.168.1.100 变为 192.168.1.132。
   - 证据：App 通知栏现显示 http://192.168.1.132:1236/mcp。
   - 修复建议：用新 IP 重配 MCP 客户端。
   - 验证方式：重试 list_sources。
   ```

## 示例 3：调试超时

**用户**：*“调试半天没结果，最后说调试超时。”*

1. 分类 → **E5 调试/求值超时**。
2. 最小工具：`debug_source` 调大 `timeoutSec` 重试。
3. 排查：默认 120s 对慢站不足；用更小 `key` 缩小范围；必要时 `get_http_logs` 看请求是否真正返回。
4. 结论：
   ```
   - 根因：目标站点响应慢，120s 内未完成解析。
   - 证据：返回末尾“调试超时 120s，以上为已收到的部分日志”。
   - 修复建议：timeoutSec 调至 300 重试；或对具体 URL（而非关键词）调试。
   - 验证方式：重试 debug_source 应拿到完整日志。
   ```

## 示例 4：未找到书源

**用户**：*“debug_source 说未找到书源。”*

1. 分类 → **E3 未找到书源**。
2. 最小工具：`list_sources` 拿准确 URL。
3. 排查：常见原因——URL 大小写、尾部斜杠、协议 http/https 不一致，或书源确实不存在。
4. 结论：
   ```
   - 根因：传入的 bookSourceUrl 少了一个尾斜杠，与库中记录不一致。
   - 证据：list_sources 显示实际为 https://example.com/。
   - 修复建议：使用 list_sources 返回的准确 URL 重试。
   - 验证方式：debug_source 用准确 URL 应正常进入调试。
   ```

## 示例 5：调试通道占用

**用户**：*“报‘调试通道占用中，请稍后重试’。”*

1. 分类 → **E4 调试通道占用**。
2. 最小动作：等待后重试（`debug_source`/`eval_js`/`check_source` 共用通道，**勿并行**）。
3. 结论：
   ```
   - 根因：上一个校验/调试尚未结束，通道被占用。
   - 证据：工具返回“调试通道占用中，请稍后重试”。
   - 修复建议：串行调用三个共用通道的工具，等待前一个完成。
   - 验证方式：数秒后重试 debug_source。
   ```

## 示例 6：JS 错误

**用户**：*“eval_js 返回 -- 错误 --，下面一串异常。”*

1. 分类 → **E6 JS 错误**。
2. 最小工具：`get_source` 检查脚本 → `eval_js` 分步验证。
3. 排查：
   - 先跑最小脚本确认环境正常；
   - 再逐段跑出错逻辑，定位到具体函数/行；
   - 结合 `java.log` 输出的异常栈定位根因。
4. 结论：
   ```
   - 根因：脚本里调用了未定义的 getSearchResult()（函数名拼写错误）。
   - 证据：eval_js 异常栈提示 ReferenceError: getSearchResult is not defined。
   - 修复建议：将函数名改为已定义的 search() 并传参。
   - 验证方式：保存后 debug_source 以关键词重跑。
   ```

## 示例 7：Cookie 异常

**用户**：*“书源请求说要登录，但明明已经登录过。”*

1. 分类 → **E7 Cookie 异常**。
2. 最小工具：`get_cookies` 读取现状。
3. 排查：比对登录所需字段；缺失/过期 → `set_cookie` 补写（分号分隔 `name=value`，合并写持久层）；改后 `debug_source` 复测。
   - 注意 `clear_cookies` 会同时清持久/会话/WebView，不可恢复，仅在确认重置登录态时使用。
4. 结论：
   ```
   - 根因：登录 Cookie 过期，持久层缺失 token 字段。
   - 证据：get_cookies 返回的 Cookie 中无 token。
   - 修复建议：用 set_cookie 补写 token（或引导用户重新登录一次以刷新 Cookie）。
   - 验证方式：debug_source 复测应进入已登录状态。
   ```

## 示例 8：批量校验未完成

**用户**：*“check_source 有好多 [未完成]。”*

1. 分类 → **E8 批量校验未完成**。
2. 最小工具：确认状态 → `check_source` 重试。
3. 排查：
   - “未完成”≠失败：可能校验期间书源被删/重存，或结果快照缺失；
   - “校验服务未能启动” → 请用户将 App 切到前台；
   - 避免校验与 `debug_source` 并发（共用通道）。
4. 结论：
   ```
   - 根因：校验期间 App 退到后台，校验服务未能启动。
   - 证据：返回“校验服务未能启动，请将应用置于前台后重试”。
   - 修复建议：App 保持前台，分批重跑 check_source（≤50/批）。
   - 验证方式：重跑后未完成项转为通过/失败。
   ```

## 示例 9：HTTP 日志为空

**用户**：*“get_http_logs 是空的。”*

1. 分类 → **E9 HTTP 日志异常**。
2. 最小工具：`set_http_log_recording(true)` → 复现 → `get_http_logs`。
3. 结论：
   ```
   - 根因：HTTP 日志记录开关未开启。
   - 证据：get_http_logs 提示“HTTP 日志记录未开启”。
   - 修复建议：先开启记录，再让用户复现问题，之后读取。
   - 验证方式：复现后 get_http_logs 应出现记录。
   ```
